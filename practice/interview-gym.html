Say it well: turn what you know into answers that sound like it

Knowing the material and wording it under pressure are separate skills. The second one improves fast with a few fixed shapes, a bank of phrases, and practice out loud. Use the coach at the bottom, or the Say it better button on any question in the other tabs.

Five rules that fix most answers

  1. Answer first. Your first sentence is the answer, not the background. “I’d use a queue here, because…” not “So, well, there are lots of ways…”
  2. Say how many parts. “Three things matter: X, Y and Z.” The listener relaxes, and you can’t ramble past three.
  3. One real example. A single concrete case from your work beats five general points. “We hit exactly this in month-end invoicing…”
  4. Name the trade-off. Seniors sound senior because they say what a choice costs. “It’s simpler, but we lose…”
  5. Stop, then offer more. End at 60 to 90 seconds with “I can go deeper on X if that’s useful.” Silence after a good answer is fine.

Answer shapes

Pick the shape that matches the question, then fill it in. Each step is roughly one sentence.

Explain a concept

“What is X?”

  1. What it is, in one line
  2. Why it exists: the problem it solves
  3. How it works, in two or three points
  4. Where you’ve used it, or would
  5. The gotcha or trade-off

“Idempotency means doing something twice has the same effect as once. It matters because networks retry… We use idempotency keys on… The catch is you have to store…”

Compare X and Y

“X or Y?”

  1. The one-line difference
  2. When X wins
  3. When Y wins
  4. What you’d pick here, and why

“The main difference is who needs the message. A queue gives each message to one worker… a topic gives everyone a copy… Here, with three consumers, I’d use…”

“How would you…?”

Approach questions

  1. Clarify the goal and constraints
  2. The steps, in order
  3. The main risk and how you’d reduce it
  4. How you’d know it worked

“First I’d confirm what ‘slow’ means in numbers… then I’d trace one slow request… the risk is guessing, so… I’d know it’s fixed when p95 drops below…”

Behavioural (STAR)

“Tell me about a time…”

  1. Situation: one sentence of context
  2. Task: what you owned
  3. Action: three things you did
  4. Result: with a number
  5. Learned: what you do differently now

“The month-end invoicing run was failing three times in seven… I owned the fix… I did three things… All 11 October runs completed… Now I always ask what must ship together.”

Incident or debugging story

“Walk me through a problem you solved”

  1. Impact, with numbers
  2. How you stopped the bleeding
  3. How you found the cause, with evidence
  4. The fix
  5. What stops it happening again

“A file was failing with out-of-memory every day, blocking the next day’s files… the stack trace showed it failed while loading the cache, not reading the file…”

Trade-off (“it depends”)

Open questions with no single answer

  1. “It depends on A and B.”
  2. If A, I’d do this
  3. If B, I’d do that
  4. For this case I’d pick…, because…

“It depends on how fresh the data must be and how often it changes. If seconds matter… If a few minutes is fine… For a product page, I’d cache with a short TTL because…”

System design opener

The first two minutes

  1. Restate the problem
  2. Ask about users, scale, latency, consistency
  3. Say your plan for the time
  4. Then start drawing

“Before I draw anything, can I check the scale and what matters most? … Then I’ll sketch the API, a high-level design, go deep on the hardest part, and finish with failure modes.”

“I don’t know”

When you’re stuck

  1. Say so honestly
  2. Say what you do know nearby
  3. Reason out loud to a best guess
  4. Say how you’d find out

“I haven’t used that directly. What I do know is… so I’d expect it to… If I needed to be sure, I’d check the docs and test it in a sandbox.”

Phrase bank

Starting strong

  • “Short answer: … The longer version is…”
  • “I’d do three things.”
  • “The key idea is…”
  • “In one sentence: …”

Signposting

  • “First… then… finally…”
  • “The second thing is…”
  • “To give you a concrete example…”
  • “Zooming out for a second…”

Trade-offs

  • “The cost of that is…”
  • “It’s simpler, but we give up…”
  • “I’d accept that because…”
  • “If that changed, I’d switch to…”

Owning your work

  • “I found…”, “I decided…”, “I shipped…”
  • “My part was…; the team did…”
  • “I made the call to…”
  • “I was wrong about…, so I…”

Evidence and numbers

  • “It went from 3 failures in 7 runs to none in 11.”
  • “The query read 99% of rows it didn’t need.”
  • “About [X] customers a day.”
  • “I measured it with…”

Checking in

  • “Is that the level of detail you want?”
  • “Shall I go deeper on the data model or move on?”
  • “Can I check one assumption?”
  • “I’ll pause there.”

Recovering

  • “Let me rephrase that more clearly.”
  • “Actually, I’d correct that: …”
  • “Give me a second to think.”
  • “Let me come back to that once I’ve covered…”

Closing

  • “So, in summary…”
  • “The main risk I’d watch is…”
  • “At ten times the scale, I’d change…”
  • “I can go deeper on X if useful.”

Before and after, from your own stories

“What’s the hardest problem you’ve solved?”

Before

“So there was this invoicing thing that kept breaking, it was quite complicated, there was a timeout and some stuff with the error handling, and basically I fixed a few things and added tests and it works now.”

After

“The month-end invoicing run was failing three times out of seven, and every failure needed manual database work. The cause was one partner’s slow query timing out, and an error handler that crashed instead of handling it, which took the whole batch down. I did three things: fixed the error handling so a failure couldn’t be mistaken for zero, isolated each partner so one failure only affected that partner, and added a 30-second timeout. I also added a visible Failed status after talking to Finance. All 11 runs in October completed. I can go into the testing if that’s useful.”

“Tell me about a production issue you debugged.”

Before

“There was an out-of-memory error on a file and I looked at the logs and the code and found it was loading stuff again and again so I made it load once.”

After

“A daily customer-merge file kept crashing with out-of-memory, which blocked the next day’s files too. The stack trace showed it failed while loading a cache of about 3 million customer ids, not while reading the file. In the code, each file handler reloaded that cache from scratch. I made it load once per run, with a lock so two handlers couldn’t load it at the same time. The out-of-memory errors stopped in staging, and the lesson I took was: the file that fails isn’t always the cause.”

“How do you handle security issues?”

Before

“Some of our errors were showing too much stuff, like stack traces, so I fixed that and tidied up the validation.”

After

“Error responses from our authentication and account services were exposing stack traces and SQL details, and input validation was inconsistent across the partner services. I removed internal details from every error response, so callers get a clear message and a reference id instead, and I standardised validation so malformed requests are rejected at the edge rather than reaching the database. Now malformed requests no longer cause database errors, and nothing internal leaks to callers. The lesson I took: error responses are part of the attack surface, and deserve the same review as any other output.”

Practise it

  1. Pick a question. Set a 60-second timer and answer out loud (or record a voice note).
  2. Play it back, or type what you said. Mark every filler word and anything you said twice.
  3. Use the coach below to reword it, then say the new version out loud twice.
  4. Next day, answer the same question again without looking. It should come out cleaner each time.
