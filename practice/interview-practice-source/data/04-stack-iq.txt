#DOC Backend and Frontend Stack
#SHEET Node.js
I How does Node handle many concurrent requests on one thread? || It doesn't wait for I/O. The main thread starts an operation, registers a callback or promise, and moves on. The OS (for sockets) or the libuv thread pool (for files, DNS and some crypto) completes the work, and the event loop runs the callback when it's ready. Concurrency comes from overlapping waits, not from parallel JavaScript.
I What's the difference between `process.nextTick`, promises, `setImmediate` and `setTimeout`? || `nextTick` and promise callbacks are microtasks that run before the loop continues; `nextTick` goes first in CommonJS, promises first in ES modules. `setImmediate` runs in the check phase after I/O; `setTimeout(0)` runs in the timers phase. Too many recursive microtasks can starve I/O.
I What happens if you do CPU-heavy work in a request handler, and how do you fix it? || It blocks the event loop, so every other request stalls. Fix it with worker threads or a worker pool, chunking the work, using async built-ins that run on the thread pool, or moving the job to a separate service or queue.
I How do you scale a Node service? || Run several stateless processes, one per core or as several containers, behind a load balancer. Keep state in Redis or the database, and scale on CPU and event loop delay.
I How would you track down a memory leak in Node? || Confirm heap growth from metrics, reproduce it under load, and take two heap snapshots a few minutes apart to compare what's growing. Common causes are caches without limits, listeners that are never removed, and closures holding request data.
#SHEET Express
I What is middleware, and why does order matter? || Middleware is a function in the request pipeline that can read or modify the request, respond, or call `next()`. Order matters because each one only sees what earlier middleware has done. Body parsing must come before routes that read `req.body`, auth before protected routes, and the error handler last.
I How do you handle errors in Express? || Use one central error middleware with four parameters that maps known errors (validation, not found, conflicts) to status codes and returns a safe 500 otherwise. In Express 5, rejected promises reach it automatically; in Express 4 you need try/catch or a wrapper. Errors in callbacks and event emitters still need handling.
I How would you structure a large Express app? || Group feature routers by business capability, keep handlers thin, and put business logic in services that don't import Express. Validate at the edge, pass dependencies in through an app factory, and use one error handler. Then the core logic can be tested without HTTP.
I How do you secure an Express API? || Use Helmet for headers, an allowlist for CORS, rate limiting, body size limits and schema validation. Authenticate in middleware and authorise per resource in the service, set `trust proxy` correctly, never return stack traces, and scan dependencies.
I Express, Fastify or NestJS? || Express for familiarity and flexibility. Fastify where throughput and built-in schema validation matter. NestJS when a large team benefits from enforced structure and dependency injection, at the cost of more framework to learn.
#SHEET Sequelize
I What is the N+1 problem, and how do you fix it? || One query loads a list, then one more query runs per item to load related data, so 100 items means 101 queries. Fix it with eager loading (`include`), a single batched query (`WHERE id IN (…)`), or a DataLoader-style batcher. Spot it in logs or APM traces as many near-identical queries per request.
I How do transactions work in Sequelize? || Prefer managed transactions: pass a callback, and it commits on success and rolls back on any thrown error. Every query inside must receive the transaction object, or be covered by CLS (continuation-local storage). Use row locks or an appropriate isolation level when concurrent requests may change the same rows, and keep transactions short.
I When would you use raw SQL instead of the ORM? || For complex reports and aggregations, bulk operations, database-specific features, and hot paths where you need full control of the query plan. Always use bound parameters, and keep the raw SQL inside the repository so callers don't know the difference.
I How do you change a production schema safely? || Use migrations and the expand/contract pattern. Create Postgres indexes `CONCURRENTLY`, avoid long table locks, and make each step backward-compatible with the code that's still running during a rolling deploy.
I How do you size a connection pool? || Instances × pool max must stay comfortably below the database's connection limit, with headroom for admin access and migrations. More connections isn't faster past a point. For Lambda or very spiky scaling, put RDS Proxy or PgBouncer in front of the database.
