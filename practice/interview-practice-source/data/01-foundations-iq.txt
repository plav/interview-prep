#DOC Foundations
#SHEET Basic coding principles
I What makes code good? || It's correct, easy to understand and safe to change. I use Beck's rules in order: it passes the tests, reveals its intent, has no duplicated knowledge, and has nothing unnecessary. Then I check it fits the conventions of the codebase.
I What is DRY, and when wouldn't you apply it? || The original definition from The Pragmatic Programmer is about knowledge: each business rule has one authoritative home. I don't merge code that merely looks alike when it changes for different reasons, because that couples unrelated things. If an abstraction proves wrong, I inline it and wait for the real pattern.
I Does YAGNI mean no up-front design? || No. YAGNI is about not building speculative features. It doesn't stop you keeping code easy to change, and decisions that are expensive to reverse, such as public APIs, schemas and security boundaries, still need thought up front.
I How do you handle errors? || Validate at the boundaries and fail fast with errors that carry context. Handle each error at the layer that can actually do something, whether that's retrying, falling back or returning a 4xx. Never swallow errors, log once with context rather than at every layer, and never leak internals to users.
I When do you write comments? || To explain why: business rules, constraints, workarounds and links to tickets. I also write doc comments for public APIs. If a comment explains what the code does, I try renaming or extracting first.
I How do you know a function is too big? || It's hard to name without "and", it mixes levels of detail like parsing, rules and I/O, or it needs heavy mocking to test. Line count is a weak signal on its own.
I Live task: "Improve this messy function." || Talk through the approach. First, pin current behaviour with a quick test. Then rename for meaning, add guard clauses to flatten nesting, extract the pure logic from the I/O, and replace magic values with named constants. Rerun the tests after each step, and say out loud which trade-offs you're choosing not to make yet.
#SHEET Advanced coding principles
I Explain SOLID, and tell me when you wouldn't apply it. || Give one line per letter, then the judgement. SRP is about separating code that different stakeholders change. Dependency inversion is most valuable at I/O boundaries. Open/closed only matters where variation is proven. I wouldn't add interfaces or extension points where nothing varies, because indirection has a reading cost.
I Composition or inheritance? || Composition by default. Inheritance couples a child to its parent's internals and creates fragile base classes. I use it for genuine is-a relationships with a stable base, or when a framework expects it.
I What is dependency injection, and why use it? || A component receives its collaborators instead of creating them. That makes dependencies visible, lets tests pass fakes, and lets you swap implementations. You don't need a container: constructor injection plus one composition root is often enough.
I How do you use the type system to prevent bugs? || I model states as discriminated unions so invalid combinations can't compile, and add exhaustiveness checks with `never`. I parse untrusted input at the boundary instead of casting, use branded types for IDs that are easy to mix up, and keep `strict` on with no `any` in domain code.
I How do you test code with lots of side effects? || Restructure it: pull the decisions into a pure functional core and leave a thin shell for the I/O. The core gets fast unit tests with plain data, and the shell gets a few integration tests. Inject time and randomness rather than reading them inside the logic.
I When would you return an error rather than throw? || Return typed results for expected outcomes the caller must handle, such as validation failures, not found or a declined payment. Throw for bugs and infrastructure failures that should propagate. Then follow the team's convention consistently.
#SHEET Production-grade code
I What makes code production-ready? || It handles failure (timeouts, safe retries, validation), it's observable (logs, metrics, traces, alerts), and it's operable (config, health checks, graceful shutdown). It can also be deployed and rolled back safely. Correct business logic is the starting point, not the finish line.
I How would you design retries? || Retry only transient errors, with capped exponential backoff and jitter so clients don't retry in sync. Keep attempts low, retry at a single layer, keep the total within the caller's deadline, and only retry operations that are idempotent.
I What is idempotency, and how do you implement it? || Repeating a request has the same effect as sending it once. The client sends a unique key; the server stores the key with the outcome, enforced by a unique constraint, and replays the stored result for duplicates. Decide how long keys live and what counts as "the same request".
I Liveness vs readiness? || Liveness detects a stuck process and triggers a restart, so it should be cheap and shallow. Readiness decides whether to send traffic and can check dependencies. It should also fail during shutdown.
I How do you ship a breaking database change? || Use expand and contract. Add the new column or table, deploy code that writes to both, backfill, switch reads to the new shape, then remove the old one in a later release. Each step is backward-compatible and can be rolled back.
I How would you investigate a latency spike in production? || Mitigate first: if a deploy lines up with the spike, roll back. Then check rate, errors and duration per endpoint, use traces to find the slow step, and check dependency health and saturation (CPU, connection pools, queues).
#SHEET Basic engineering principles
I Tell me about a mistake you made in production. || Behavioural: answer with a real STAR story. Pick a real one. Show that you owned it, mitigated first, communicated clearly, and then fixed the system, not just the symptom, through a blameless review. End with what changed afterwards.
I How do you approach a task you've never done before? || Clarify the goal and constraints, read the existing code and docs, and do a small timeboxed spike. Then deliver in thin slices and ask targeted questions early.
I How do you balance speed and quality? || Use reversibility and blast radius. Move fast on two-way doors behind flags, and slow down on one-way doors such as data models and public APIs. When time is short, cut scope rather than quality, and record any shortcut as debt.
I Tell me about a technical disagreement. || Behavioural: answer with a real STAR story. Show that you understood their view, used data or a small experiment, and reached a decision. If it went the other way, you committed fully. Avoid stories where you were simply right.
I What does ownership mean to you? || Caring about the outcome rather than the ticket: monitoring after release, fixing what you find, writing the runbook, and closing the loop with stakeholders.
#SHEET Advanced engineering principles
I How would you set reliability targets for a new service? || Start from the critical user journeys and choose SLIs for them, such as successful checkouts and p95 latency. Set SLOs from user needs and historical data, agree an error budget policy with product, and alert on burn rate rather than raw metrics.
I How do you prioritise technical debt? || By interest: how often the code changes, how much it slows delivery or causes incidents, and what fixing it unlocks. Attach debt work to the roadmap where possible, and track the outcome, such as lead time or incident count.
I How do you estimate a large project? || Break it into pieces and estimate each as a range. Identify the riskiest unknowns and spike them first. Give an overall range with a confidence level, then re-forecast at milestones and communicate changes early.
I How do you influence a decision you don't own? || Understand what the decision-makers care about, then write up the options and trade-offs with data or a prototype. Talk to key people before the meeting. Once it's decided, commit, even if it went the other way.
I What is Conway's law, and why does it matter? || Systems mirror the communication structure of the teams that build them. If service boundaries don't match team boundaries, you get coordination overhead and tangled code. You can design team structure to get the architecture you want.
I Tell me about a system you made more reliable. || Use STAR and give numbers: the starting SLO or incident rate, what you changed (alerts, timeouts, rollout process), and the measurable result.
#SHEET Basic design principles
I What are coupling and cohesion? || Cohesion is how strongly the parts of a module belong together; coupling is how much modules depend on each other's details. You want high cohesion and low coupling, so a change stays inside one module.
I How do you decide where module boundaries go? || Around decisions likely to change, following Parnas: vendors, storage, formats, business rules. Also around business capabilities, and around what changes together and who owns it.
I Explain hexagonal architecture. When is it worth it? || The business logic sits in the middle and talks to the outside world through ports, meaning interfaces it owns. Adapters connect those ports to HTTP, databases and vendors. It's worth it when you need to test logic in isolation or expect to swap infrastructure; for a thin CRUD app it can be overkill.
I Which design patterns have you used, and why? || Pick two with real stories. For example, an adapter around a payment SDK so you could switch vendors, and middleware (a decorator) for auth and logging in Express. Explain the problem each one solved, not the textbook definition.
I What is a leaky abstraction? || An interface that forces callers to know about what it hides, such as a repository returning ORM objects or a gateway throwing vendor errors. Fix it by translating at the boundary.
#SHEET Advanced design principles
I Monolith or microservices? || Start with a well-modularised monolith unless you already have many teams that need independent releases. Split along bounded contexts when there's a concrete reason, such as team autonomy, different scaling needs or fault isolation, and accept the operational cost that comes with it.
I How do you keep data consistent across services? || Keep strong consistency inside each service's own database. Across services, use events published through an outbox, sagas with compensating actions for multi-step processes, and idempotent consumers. Then design the user experience for eventual consistency, for example by showing an order as "processing".
I What is a bounded context? Give an example. || It's the boundary within which one model and its vocabulary are consistent. "Product" in the catalogue (descriptions, images) differs from "product" in the warehouse (stock levels, bin locations). Each context owns its model and translates at the edges.
I How would you migrate a legacy system? || Put a facade or proxy in front of it and add characterisation tests around current behaviour. Move one capability at a time to the new system, routing its traffic over, and migrate the data that capability owns. Delete the old code as you go, and keep each step reversible.
I What is an aggregate, and why does it matter? || It's a consistency boundary: a group of objects that change together through one root, which enforces the invariants. Keeping each transaction to one aggregate keeps locking small and makes the boundary easy to scale.
#SHEET Frameworks
I How would you review an architecture? || Walk the Well-Architected pillars, run a STRIDE pass on trust boundaries, and ask what happens when each dependency is slow or down. Then check cost at the expected scale, and confirm decisions are recorded in ADRs.
I How do you document a system? || C4 context and container diagrams for the big picture, ADRs for the why, runbooks for operations, and READMEs for getting started. Keep diagrams as code in the repo so they're reviewed with changes.
I How do you measure a team's delivery performance? || Use the DORA metrics as trends: throughput (lead time, deployment frequency, recovery time) alongside instability (change fail rate, rework rate). Pair them with SLOs for user impact, and never use them to rank individuals.
I How would you threat-model a new feature? || Draw the data flows, mark the trust boundaries, and go through STRIDE for each element that crosses one. Record mitigations with owners, and revisit when the design changes.
